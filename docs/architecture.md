# 从广告事件到赞助推理

产品需要三个协作部分：客户端展示与明确接受、受控宿主的请求路由、服务端的预算与计费网关。普通 Skill 文本不能安全地替换任意宿主的账户。

```text
用户接受 → 宿主固定报价 → 预算池预留 → 有限赞助请求 → 用量扣减 / 余款释放
                 ↓
       广告加载 → 展示 → 服务端验真 → 授信幂等核销
                 ↓
       平台报表 → 反作弊 → 结算单 → 现金到账
```

三个独立状态：广告资格已验真、授信已核销、现金已到账。不得把前两个当作第三个。当前实现只模拟前两类事件，外部真实收入固定为零。

沙箱按运行标识稳定选择三档示例 eCPM，把模拟价值按比例折算为模型预算，先扣除输入预留，再按输出示例价格、量化单位和上限生成额度。所有金额使用整数微元；报价只能由宿主创建，客户端不能提交奖励金额。

每次模型请求需要独立预算准入；上下文变长可能导致额度不足，不能因此偷偷退回用户付费账户。完整宿主参考处理显式恢复选择、同一会话的运行身份与幂等回调。独立 demo 只演示报价及签名，不执行真实请求或发放实际 Token。

生产系统不能复用本地进程内签名作为广告平台证明，也不能使用会在重启后重置的内存池作为真实账本。必须采用平台允许的服务端验证、持久原子预算和独立凭据，并在验真前严格限制临时过桥额度。
